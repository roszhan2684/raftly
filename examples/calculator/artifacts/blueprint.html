Product

From PRODUCT.md and requirements.yaml.

Problem

People use calculators dozens of times a week for prices, tips, splits and quick sums. Built-in calculators hide the expression (users lose track mid-calculation), disagree on precedence and percent, and on the web often show floating-point artefacts such as 0.30000000000000004. The cost is small but frequent: re-typing, doubt, and occasional wrong answers. See RESEARCH.md #3–#4.

ICP

Anyone doing quick everyday arithmetic on a phone or laptop: shoppers, students, freelancers splitting invoices, people at a restaurant. The primary early adopters are detail-minded users annoyed by calculators that hide the expression.

Positioning

For everyday calculator users who want to trust the answer, Tally is a calculator for mobile and the web that shows exactly what it will compute and gets decimals right. Unlike built-in calculators, it keeps the whole expression visible and never shows floating-point noise.

Differentiation

Correctness (exact decimals, documented semantics), visibility (live expression line), speed (offline, instant), reuse (history), accessibility, and no data collection.

Design

From DESIGN.md.

Chosen direction

Option B: Modern utility (ADR-005, RECOMMEND, confidence 75). It makes the product's promise visible without sacrificing familiarity. Validate in EXP-001 interviews.

Design direction options

Option A — Native minimal

Mirrors platform calculators: one result line, keypad, history hidden behind a gesture.

|            1,284 |
| C  ±  %  ÷ |
| 7  8  9  × | ...

Strengths: zero learning. Weaknesses: indistinguishable from the built-in app (R-003); hides the expression. Accessibility: simple. Best for: users satisfied with what they have (that is, not our ICP).

Option B — Modern utility (recommended)

Two-line display: the expression line (12 × (3 + 4)) and a large result with a live preview in a muted tone until =. A history drawer is one swipe away; copy sits next to the result.

|      12 × (3 + 4) |
|              = 84 |  [copy]
| C  (  )  ÷ |
| 7  8  9  × |
| 4  5  6  − |
| 1  2  3  + |
| ±  0  .  = |   [history ▲]

Strengths: makes precedence and percent visible (R-005), and expresses the differentiators. Weaknesses: a busier display, which needs careful type scale. Accessibility: two announcement streams (debounce). Best for: our ICP.

Option C — Workspace / history-first

A notebook-like list of calculation lines that can be edited and re-run, with the keypad below. Strengths: power-user reuse. Weaknesses: cramped on phones; more build effort. Best for: tablet/desktop power users. Post-V1 candidate.

Information architecture

Entities: the current expression, the result, history entries. One primary screen (SCR-main) plus a history surface (SCR-history). No settings screen in V1 (theme follows the system; haptics follow the system).

Key screens

SCR-main — Calculator
  • Purpose: enter and evaluate expressions.
  • Primary actor / action: end user / tap =. Secondary: copy, clear, backspace, open history.
  • Data shown and hierarchy: result (largest) → expression → keypad. The preview uses the muted text token until evaluated.
  • States: default 0 · typing (expression + preview) · evaluated · error ("Can't divide by zero", in the danger text token, no modal) · empty (shows 0) · no loading state (local).
  • Permissions: none.
  • Desktop: keypad max width 420 px, centred; history as a side panel ≥ 900 px. Tablet: same as desktop at ≥ 700 px. Mobile: full-bleed keypad; display takes the top 35%.
  • Keyboard (web): see F004; ? opens shortcuts.
  • Accessibility: labelled keys, live region for results (debounced 400 ms while typing), 44pt/48dp targets, reflow at 200% text.
  • Analytics: none (ADR-008).
SCR-history — History
  • Purpose: reuse past results.
  • Primary action: tap a result to insert it. Secondary: restore the expression, copy, clear all.
  • Data: expression, result, relative time; newest first; max 100.
  • States: empty ("Your calculations will appear here. History stays on this device.") · list · storage-unavailable note · confirm-clear inline.
  • Desktop/tablet: side panel; mobile: bottom sheet at 70% height.
  • Keyboard: focus trap while modal, Escape closes, arrow keys move between entries.
  • Accessibility: entries announced as "12 times 7 equals 84, 2 minutes ago".

Accessibility

Target WCAG 2.2 AA (REQ-005): contrast verified per token pair; full keyboard on web; screen-reader labels and announcements; reduced motion removes press animations; haptics are optional.

Architecture

System overview

A client-only application (ADR-001). One Expo/React Native codebase renders on iOS, Android and the web via react-native-web (ADR-004). All arithmetic happens in a pure TypeScript engine (ADR-002) using decimal.js (ADR-003). History is stored on the device.

Decisions

Chronological Decision Book. Overrides and superseded decisions stay visible.

  1. ADR-001Client-only architecture: no backend, accounts or databaseACCEPTEDType-1
    2026-10-24 · architect · RECOMMEND · confidence 92 · reversibility medium
    Constitution 4–5: the simplest architecture that satisfies actual requirements. A backend would add accounts, personal data, uptime and cost with no V1 user outcome.
  2. ADR-002One pure TypeScript calculation engine shared by all surfacesACCEPTED
    2026-10-24 · architect · AUTO · confidence 95 · reversibility high
    Separating the calculation engine from the UI (spec §55) makes the hardest part exhaustively testable and portable.
  3. ADR-003Decimal arithmetic with decimal.js instead of binary floating pointACCEPTED
    2026-10-24 · frontend · RECOMMEND · confidence 90 · reversibility high
    Correctness is the differentiator. A mature, dependency-free MIT library beats owning arbitrary-precision code.
  4. ADR-004Expo + React Native Web as the single cross-platform codebaseACCEPTEDType-1
    2026-10-24 · mobile · RECOMMEND · confidence 72 · reversibility low
    Expo documents first-class web support from the same codebase via react-native-web, with static rendering and npx expo export --platform web for production builds (checked 2026-10-24).
  5. ADR-005Design direction B: Modern utility (live expression line + history drawer)ACCEPTED
    2026-10-24 · design-director · RECOMMEND · confidence 75 · reversibility high
    B directly expresses the differentiators: you see exactly what will be computed (precedence, percent) and can reuse results. That reduces the confusion risk R-005 while keeping the familiar keypad.
  6. ADR-006Calculator semantics: expression entry with precedence, repeated equals, percent rulesACCEPTED
    2026-10-24 · product-director · RECOMMEND · confidence 80 · reversibility medium
    Predictability and visibility over cleverness. Each rule is shown by the live expression line (ADR-005).
  7. ADR-007Build the keypad and display internally; no UI component libraryACCEPTED
    2026-10-24 · design-systems · AUTO · confidence 90 · reversibility high
    Spec §9: "For a trivial component, building internally can be the senior decision." A keypad is a grid of buttons.
  8. ADR-008No analytics or telemetry in V1ACCEPTED
    2026-10-24 · privacy · RECOMMEND · confidence 85 · reversibility high
    Minimisation (privacy-compliance.md). "Collects no data" is a genuine feature for a utility.

Launch

Launch plan

  1. Closed beta (TestFlight / Play internal testing / unlisted web URL) with 20 users for 2 weeks (EXP-001).
  2. Decide on EXP-001: proceed, or stop investing beyond V1 (kill criteria).
  3. Public release: web first (instant rollback), then the stores with phased release.

Rollback

  • Web: redeploy the previous static build (one CI job); service worker updates on the next launch.
  • Stores: halt the phased release; ship a fix build. Rehearsed in N006 (G-ROLLBACK).
